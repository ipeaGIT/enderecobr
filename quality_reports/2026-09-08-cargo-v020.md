# Verificação de Cargo.lock e enderecobr_rs v0.2.0

## Diagnóstico

Não foi reproduzida uma inconsistência entre Cargo.lock e as fontes vendorizadas.
O manifest e o lock já selecionavam enderecobr_rs 0.2.0. O pacote enderecobr
0.1.0 presente no lock é o wrapper local: sua versão não precisa coincidir com
a dependência enderecobr_rs nem com a versão do pacote R.

- `cargo metadata --locked --offline --format-version 1`, executado em
  `src/rust`, resolveu todas as dependências sem modificar o lock.
- `cargo build --locked --offline --lib --target x86_64-pc-windows-gnu`, com
  diretório de saída novo, passou (55,17 s).
- O mesmo build passou usando uma cópia dos arquivos rastreados e uma extração
  nova de `src/rust/vendor.tar.xz` (94 s). Essa cópia incluiu as correções abaixo.
- A execução a partir da raiz com apenas `--manifest-path src/rust/Cargo.toml`
  não utiliza `src/.cargo/config.toml`; o erro de cache offline nesse caso não
  demonstra um defeito no lock. Executar a partir de `src/rust` usa a configuração
  local existente.

## Correção

A dependência enderecobr_rs 0.2.0 declara Rust mínimo 1.81. O wrapper e
DESCRIPTION ainda declaravam 1.65. Ambos foram alinhados para 1.81, com nota
em NEWS.md. O lock e o arquivo vendor não precisaram de regeneração.

SHA-256 preservados:

- Cargo.lock: `8B6ED6E8FE725367F97209A6BA3A5AA3D7AF70DCFACFE597CF43AA2DD50CD95A`
- vendor.tar.xz: `1BA418838F376F7BE006D8B15ABC053B0D483BBD8F9FB08B68622D6B9A357EA1`

## Ambiente e limites

Cargo 1.87.0; target x86_64-pc-windows-gnu instalado. O sandbox impediu a
execução inicial de rustc; os builds passaram após autorização para execução
fora dele. O R padrão é 4.6.0; não há Rtools 4.6 detectável. A validação R usa
R 4.5.1 e Rtools 4.5, em uma cópia isolada para preservar src/vendor preexistente.
O teste de compilação C desse ambiente passou fora do sandbox.

`devtools::test()` não chegou a executar os testes: durante o build do binário
`document`, Cargo encontrou bloqueios de arquivo do Windows (`os error 32`) ao
remover diretórios temporários de arquivos .rlib. O problema voltou a ocorrer
em outra dependência após nova tentativa. Não foi identificado o processo que
mantinha o bloqueio.

Uma tentativa intermediária revelou também que o linker padrão
`x86_64-w64-mingw32-gcc` não estava disponível. Na tentativa seguinte foi definido,
somente no processo R:

```r
Sys.setenv(
  CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER =
    "C:/rtools45/x86_64-w64-mingw32.static.posix/bin/gcc.exe"
)
```

Essa tentativa voltou a falhar por bloqueio de arquivo antes dos testes. Logs:
`cargo-v020-r45-tests.log`, `cargo-v020-r45-tests-retry.log` e
`cargo-v020-r45-tests-linker.log`. Não são falhas de resolução de Cargo.lock.

Ainda é necessário obter a mensagem e o comando originais do usuário para
identificar a causa específica do erro relatado. R CMD check --as-cran e a
matriz de CI não foram executados; não houve commit, merge ou release.

## Erro original de devtools::load_all()

A mensagem original confirmou que Cargo.lock não era a causa. O primeiro
`cargo build --lib` não vincula um executável e passava. O comando seguinte,
`cargo run --bin document`, precisava vincular `document.exe` e falhava porque:

1. Cargo inferia o linker `x86_64-w64-mingw32-gcc`, inexistente no Rtools 4.5
   instalado, cujo compilador exposto ao build do R é `gcc`.
2. Depois de selecionar `gcc`, esse segundo comando ainda não recebia o
   `LIBRARY_PATH` que contém o mock `libgcc_eh.a` criado pelo próprio Makevars.
3. Os dois comandos usavam RUSTFLAGS diferentes, obrigando Cargo a recompilar
   todas as dependências durante a geração dos wrappers e aumentando a chance
   dos bloqueios de arquivo observados no diretório sincronizado pelo Dropbox.

Correções aplicadas em `src/Makevars.win.in` e `tools/config.R`:

- gerar a variável Cargo específica do target, por exemplo
  `CARGO_TARGET_X86_64_PC_WINDOWS_GNU_LINKER`;
- defini-la como o primeiro token de `$(CC)`, removendo o espaço final que R
  acrescenta ao valor `gcc `;
- fornecer o mesmo `LIBRARY_PATH`, RUSTFLAGS e perfil aos dois comandos Cargo.

Validação final com R 4.6.0, Rtools 4.5, cargo/rustc 1.87.0 e target
`x86_64-pc-windows-gnu`:

- `devtools::load_all('.')`: instalação concluída com `* DONE (enderecobr)`;
- `cargo run --bin document`: vinculou e executou `document.exe`;
- `devtools::test('.', reporter = 'summary', stop_on_failure = TRUE)`: todos os
  testes passaram (`TESTS_OK`).

Permanece apenas um aviso ambiental: o `testthat` instalado foi construído com
R 4.6.1, enquanto o R usado na validação é 4.6.0. Não afetou os testes. O
diretório não rastreado `src/vendor`, apagado pelo cleanup normal do build, foi
restaurado a partir de `src/rust/vendor.tar.xz`.
