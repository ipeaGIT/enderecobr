## Core Principles

- **Plan first** — enter plan mode before non-trivial tasks; save plans to `quality_reports/plans/`
- **`R/` is authoritative** — `man/` and `NAMESPACE` are generated by roxygen2. Never hand-edit; edit the roxygen blocks in `R/` and run `devtools::document()`
- **Two backends, one release gate.** `R CMD check --as-cran` (0 errors, 0 warnings, every note justified in `cran-comments.md`) gates the R side. A clean `cargo build` of `src/rust/` against the pinned `enderecobr_rs` version gates the Rust side — both must pass before merge or release.
- **`enderecobr_rs` is upstream, not vendored source.** The actual standardization logic lives in the sibling repo `ipeaGIT/enderecobr_rs` (published on crates.io). `src/rust/` here is a thin extendr wrapper crate around it. A reported bug is usually fixed **there** first — pulling the fix into this package means bumping the version pin in `src/rust/Cargo.toml`, not patching logic here. See [`r-extendr-conventions.md`](~/.claude/rules/r-extendr-conventions.md) (global rule).
- **`[LEARN]` tags** — when corrected, or a non-obvious approach is confirmed, append `[LEARN:category] wrong → right` to [MEMORY.md](MEMORY.md)

Content sections (matching `r-package-conventions.md`'s style/structure):
1. **Anatomy** — extendr wrapper crate vs. upstream logic crate; `R/extendr-wrappers.R` is generated, never hand-edit.
2. **The upstream-dependency pattern** — when a bug is reported, check whether the fix belongs upstream (in the logic crate) or in the wrapper (`src/rust/src/lib.rs`); bumping the pinned version in `Cargo.toml` + `cargo update -p <crate> --precise X.Y.Z` is how upstream fixes land here. Cross-repo issue numbers do **not** correspond between the wrapper package and the upstream crate — verify fixes empirically (reproduce the reported example), never by matching issue/commit numbers across repos.
3. **rextendr regeneration** — `rextendr::document()` only when the extendr-exposed function signatures change; a pure internal fix upstream needs no regeneration.
4. **CRAN offline vendoring** — `cargo vendor` → `vendor.tar.xz` + `vendor-config.toml`; regenerate whenever `Cargo.lock` changes; stale vendor tarballs are a silent CRAN-build failure, not a check ERROR you'd catch locally.
5. **MSRV & multi-platform builds** — `tools/msrv.R` gate, `configure`/`configure.win` → `src/Makevars(.win)` generation, Windows ARM64 target triple handling.
6. **Checklist** (mirroring `r-package-conventions.md` §8's format).
